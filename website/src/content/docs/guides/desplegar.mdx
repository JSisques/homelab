## 0. Antes de tocar nada

Todo esto se ejecuta desde una **máquina de control** (tu portátil, o el runner que uses) — no desde el propio Proxmox.

- Proxmox instalado y accesible en la red, con una plantilla cloud-init y un **API token** de una cuenta de servicio ya creados — ver [Preparar Proxmox para Terraform](/homelab/guides/preparar-proxmox/) si todavía no existen.
- [`yq`](https://github.com/kislyuk/yq) instalado — el de **kislyuk** (jq wrapper), no el de mikefarah (sintaxis distinta, incompatible con los generadores). Si tienes el otro instalado, los generadores fallan con errores de `jq` que no tienen mucho sentido a simple vista.

  En Debian/Ubuntu está directamente en apt y es el mismo binario/paquete (no hace falta pip ni instalar Python aparte — `apt` ya resuelve `jq` y `python3` como dependencias):

  ```bash
  sudo apt install yq
  ```

  Solo hace falta `pip install yq` en distros donde ese paquete no exista en los repos.
- Terraform y Ansible instalados (`ansible-core` + `ansible-galaxy`).
- Una plantilla de LXC Debian ya subida a Proxmox (para `debian_template`), y la clave pública SSH a mano.

:::note[¿Y Docker?]
No hace falta instalarlo a mano en ningún sitio. **Nunca** corre en el propio Proxmox — solo es el hipervisor. Dentro de cada LXC lo instala Ansible automáticamente (rol `docker`, dependencia obligatoria de todo rol de servicio, ver `ansible/roles/docker/`). En tu máquina de control solo importa si además quieres correr `make validate` en local (usa `docker compose config` para comprobar la sintaxis de los ficheros `compose.yaml`) — si no, esa misma validación ya la hace `ci.yaml` en GitHub Actions.
:::

## 1. Desplegar de cero

<Steps>

1. **Rellena lo que hoy es un placeholder.** Dos cosas no tienen todavía un valor real:

   | Fichero | Qué falta |
   | --- | --- |
   | `config/hosts.yaml` | `proxmox: address: TBD` → la IP real del hipervisor |
   | `terraform/proxmox/terraform.tfvars` | no existe (está en `.gitignore` a propósito) — cópialo de `terraform.tfvars.example` y rellena `proxmox_node`, `lxc_storage`, `vm_storage`, `gateway`, `ssh_public_key`, `debian_template` |

   ```bash
   cp terraform/proxmox/terraform.tfvars.example terraform/proxmox/terraform.tfvars
   # edítalo con tus valores reales

   export TF_VAR_proxmox_endpoint="https://<ip-proxmox>:8006/"
   export TF_VAR_proxmox_api_token="user@realm!tokenid=uuid"
   ```

2. **Genera y provisiona la infraestructura.**

   ```bash
   make generate   # hosts.auto.tfvars.json, inventario, Homepage y Prometheus al día
   make init
   make plan       # revisa el plan: hoy son 15 LXC + 2 VM (pbs, k3s-server) nuevas
   make apply
   ```

3. **Configura los servicios dentro de esas LXC/VM**, uno a uno la primera vez:

   ```bash
   cd ansible && ansible-galaxy collection install -r requirements.yml && cd ..
   make ping        # confirma que Ansible llega por SSH a todos los hosts
   make services    # lista los nombres válidos para deploy-<nombre>

   make deploy-monitoring
   make deploy-homepage
   make deploy-uptime-kuma
   make deploy-it-tools
   make deploy-n8n
   # ...y así con el resto: obsidian, jellyfin, downloads,
   # adguard-home-1, adguard-home-2, adguard-home-sync (en ese orden —
   # sync necesita que las dos instancias ya existan),
   # traefik, wireguard, pbs, promtail, k3s-server, rustfs, cookidoo-mcp
   ```

   `cloudflared` se deja para el final — necesita su [configuración manual de una sola vez](#cloudflare-tunnel) antes de poder desplegarse. Antes de desplegar un servicio concreto, exporta los secretos que le correspondan (ver la [tabla de abajo](#secretos)) — sin ellos algunos roles simplemente fallan (`assert`) y otros arrancan con un valor por defecto inseguro.

</Steps>

:::note[¿Por qué no `make deploy` directamente?]
`make deploy` despliega *todo* de una sentada, incluido `cloudflared`. La primera vez es más seguro ir servicio a servicio como arriba — así un fallo queda acotado a un único rol.
:::

## Día a día

### Cambiar la configuración de un servicio que ya existe

```bash
# ejemplo: subir la RAM de n8n
# 1. edita config/hosts.yaml -> n8n: memory: 8192
make plan          # confirma que solo toca la LXC de n8n
make apply
make deploy-n8n     # por si el compose también cambió
```

### Añadir un servicio nuevo por completo

<Steps>

1. Entrada nueva en `config/hosts.yaml` (dirección, `cpu`/`memory`/`disk`, `role`) y en `config/services.yaml` (tier, url, si aparece en Homepage/Prometheus).
2. `services/<nombre>/compose.yaml` — el Compose real.
3. `ansible/roles/<nombre>/` — `defaults`, `tasks` (copiar el compose y arrancarlo, mismo patrón que `it-tools`) y `meta/main.yml` con la dependencia obligatoria de `common` + `node-exporter` + `docker`.
4. `ansible/playbooks/<nombre>.yaml` de una línea (`roles: [<nombre>]`), añadido a `ansible/playbooks/site.yaml`.
5. `make generate && make plan && make apply && make deploy-<nombre>`.

</Steps>

### Desplegar solo un servicio concreto

```bash
make services          # lista los nombres válidos
make deploy-cloudflared # it-tools · n8n · monitoring · homepage · uptime-kuma · cloudflared
```

## Secretos

Nada de esto está commiteado ni lo estará.

| Variable | Para qué | Si falta |
| --- | --- | --- |
| `N8N_POSTGRES_PASSWORD` | Contraseña de la Postgres interna de n8n | Se despliega igual, con `changeme` por defecto — riesgo silencioso |
| `COOKIDOO_MCP_EMAIL` / `COOKIDOO_MCP_PASSWORD` | Credenciales de Cookidoo para `cookidoo-mcp` | El rol falla al arrancar el contenedor |
| `CLOUDFLARED_CREDS_JSON` | Contenido completo del `credentials.json` del túnel | El rol hace `assert` y para antes de arrancar nada |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_CHAT_ID` | Notificaciones de Alertmanager | Las alertas se siguen disparando pero no llegan a ningún sitio |
| `DOWNLOADS_VPN_SERVICE_PROVIDER` / `DOWNLOADS_VPN_WIREGUARD_PRIVATE_KEY` / `DOWNLOADS_VPN_WIREGUARD_ADDRESSES` | Configuración del gateway VPN (gluetun) del stack de descargas | qBittorrent no tiene por dónde salir a internet |
| `RUSTFS_ACCESS_KEY` / `RUSTFS_SECRET_KEY` | Credenciales del object storage S3-compatible | El servicio arranca sin credenciales configuradas |
| `ADGUARD_SYNC_ORIGIN_USERNAME` / `_PASSWORD` | Credenciales de admin de `adguard-home-1`, para que `adguard-home-sync` pueda leer su config | El contenedor de sync no puede autenticarse contra el origen |
| `ADGUARD_SYNC_REPLICA_USERNAME` / `_PASSWORD` | Credenciales de admin de `adguard-home-2`, para que `adguard-home-sync` pueda escribir en la réplica | El contenedor de sync no puede autenticarse contra la réplica |

Estas son las que usa `Makefile` (`ANSIBLE_EXTRA_VARS`) para cualquier `make deploy` / `make deploy-<servicio>` — solo hace falta exportar las del servicio que estés desplegando en ese momento, el resto puede quedar vacío. En GitHub Actions (workflow `deploy.yaml`, manual) son *repository secrets*, más `PROXMOX_ENDPOINT` y `PROXMOX_API_TOKEN` para que Terraform hable con Proxmox.

## Cloudflare Tunnel

Crear el túnel exige estar autenticado contra la cuenta de Cloudflare — no hay forma de scriptearlo desde CI. Es un paso manual, **una vez**:

<Steps>

1. `cloudflared tunnel login` — autoriza la CLI contra la cuenta.
2. `cloudflared tunnel create homelab` — anota el **tunnel ID** y guarda el `credentials.json` que genera (ese es el valor de `CLOUDFLARED_CREDS_JSON`).
3. Sustituye `REPLACE_WITH_TUNNEL_ID` por el ID real en `services/cloudflared/config.yml` — ese fichero sí se commitea, no lleva secretos, solo las reglas de enrutado.
4. Por cada hostname del `config.yml` (hoy: `gardenia.sisqueslabs.com`), un registro DNS CNAME apuntando a `<tunnel-id>.cfargotunnel.com`, en las zonas de `sisqueslabs.com` y `jsisques.net`.
5. `make deploy-cloudflared` con `CLOUDFLARED_CREDS_JSON` ya exportado.

</Steps>

:::caution[Nunca en el túnel]
Los servicios `tier: internal` (`*.home.arpa`) no llevan entrada en `config.yml`. Si aparecen ahí es una fuga de un servicio interno a internet, no un despliegue normal.
:::
